# 学生请假管理系统需求说明

版本：V1.0 初步需求基线  
运行阶段：先在本地开发、运行和验收，后续部署学校服务器  
整理日期：2026-10-12

## 1. 项目目标与范围

建设独立的学生请假管理系统，采用独立数据库和本系统账号体系。通过教务提供的 Excel/CSV 导入学生资料，管理员维护组织结构、管理人员和权限。提供手机端及电脑端网页，完成请假申请、多级审批、返校定位打卡、中队长销假确认、超时提醒、查询统计和数据导出。

本说明以原始 PDF 的业务功能为依据，按照用户提出的独立系统方案调整范围。下文的状态、数据校验、异常处理和本地运行要求属于为便于开发补充的设计要求；尚未给出的学校管理规则列为配置项，不作为已经确定的校规。

### 1.1 一期必须实现

- 独立账号登录、学生数据导入、组织和管理人员维护。
- 学生请假、撤销、查看审批进度、上传证明附件。
- 根据请假类型和时长配置多级审批，支持批量审批。
- 手机定位打卡、校区电子围栏判断、中队长审核销假。
- 超时未销假提醒、分级提醒规则和待办列表。
- 按角色及管理范围查询数据、统计分析、导出结果。
- 操作日志、密码安全、附件保护、备份恢复及本地启动说明。

### 1.2 后续对接范围

| 原文功能 | 一期处理方式 | 后续扩展 |
| --- | --- | --- |
| 学籍系统自动同步 | 教务文件导入，人工更新和停用 | 学籍接口增量同步 |
| 校园统一身份认证 | 独立账号及密码 | 单点登录 |
| 企业微信移动入口及消息推送 | 手机网页、站内消息和待办 | 企业微信身份及通知接口 |
| 校园短信平台 | 站内超时提醒 | 短信通知 |
| 门禁出入记录联动 | 定位打卡加人工审核 | 门禁记录核验 |
| 信息门户、服务大厅及学校 APP | 独立网页入口 | 门户入口、待办及流程接口 |

如果原 PDF 用于合同验收，上述一期范围与原文的差异需要另行确认。本说明不将 PDF 中的七天交付、驻场人员、三年质保等采购服务条款视为本次开发指令。

## 2. 用户角色与数据权限

一个用户可以拥有多个角色；角色权限与管理范围分别配置。所有查询、审批、导出及附件访问都必须由后端校验权限。

| 角色 | 主要能力 | 数据范围 |
| --- | --- | --- |
| 学生 | 发起请假、撤销未审批申请、查看记录、提交销假 | 本人的数据 |
| 中队长 | 请假审批、批量处理、销假确认、查询及查看预警 | 所负责的班级或中队 |
| 大队长 | 按规则审批、查询统计、查看升级预警 | 所负责的大队或系部 |
| 学工处人员 | 按授权审批、查询、统计及查看预警 | 所授权的组织范围，可配置全校 |
| 分管院领导 | 按规则审批、查看统计和预警 | 所授权的院系或全校 |
| 系统管理员 | 账号、组织、角色、流程、围栏、参数和日志管理 | 系统配置；业务数据权限单独授权 |

如学校实际组织名称不同，应允许调整名称及层级，不把业务名称写死在程序中。系统管理员不因技术管理身份而自动绕过业务审批；确需代办或纠正时，必须明确授权并记录原因及前后状态。

## 3. 基础资料与账号管理

### 3.1 组织、专业、班级和校区

- 维护院系、大队、中队或班级等组织层级，以及组织之间的归属关系。
- 维护专业、入学年级、学年、学期和班级基本资料。
- 维护各班级负责的中队长、上级管理人员及生效状态。
- 维护校区及校区电子围栏，并关联学生所属校区。
- 支持启用、停用及调整归属；被历史业务引用的资料保留，不直接删除历史记录。

### 3.2 学生资料

- 基础字段：学号、姓名、院系、专业、年级、班级或中队、所属校区、学籍状态、账号状态；联系方式按实际业务需要选填。
- 学籍状态和业务在校状态分开保存。学籍状态用于在读、毕业、休学等管理；业务状态反映系统中的请假和销假情况，不作为门禁实际出入事实。
- 支持查询、维护、调班、转专业和账号停用。
- 调整学生组织时保留历史申请当时的组织信息，明确在途审批及销假由谁接管，不能产生无人处理的待办。

### 3.3 Excel/CSV 导入

- 提供导入模板和字段说明，以学号作为学生导入的唯一业务标识。
- 导入前预览，检查必填字段、重复学号、字段格式和组织匹配情况。
- 区分新增、更新、未变化及失败记录，返回错误行和原因。
- 同一份资料重复导入不生成重复学生，不覆盖历史请假数据。
- 学生批量停用应通过明确操作或导入字段完成，不因导入文件缺少某人而自动删除该学生。
- 支持导入结果报告和导入操作日志。

### 3.4 登录与密码

- 学生使用学号登录，管理人员使用管理员分配的账号登录；不开放匿名自行注册。
- 导入学生资料后创建本系统账号，不直接假定能够沿用教务系统密码。
- 提供首次激活或首次登录修改初始密码、修改密码及管理员重置功能。
- 密码保存为安全的带盐哈希，不保存或导出明文密码。
- 支持账号启用、停用、退出登录和登录失败限制。账号停用后限制继续访问。
- 未接入短信等渠道前，忘记密码通过管理员核验后重置。

## 4. 请假申请与审批

### 4.1 学生请假申请

申请字段包括请假类型、请假事由、开始时间、结束时间、是否离校、是否外宿及证明附件。外出地点、联系方式等是否必填按学校规则配置。

- 请假类型可维护，如事假、病假等，不预设为学校已确认的分类。
- 自动计算请假时长；小时、天数、跨日、节假日及取整规则按学校口径配置。
- 校验结束时间晚于开始时间，必填字段完整，附件类型和大小符合限制。
- 校验与本人已有有效申请的时间冲突，避免重复申请；哪些状态参与冲突校验应有统一规则。
- 对追补历史请假、提前申请天数及超长请假设置可配置规则。
- 提交前展示申请内容、计算时长及预计审批路线。
- 提交后生成唯一申请编号，不允许直接修改正在审批的申请内容。
- 学生可查看审批进度、节点结果、审批意见和时间。
- 原文允许未审批申请撤销；一期按“尚无人完成审批的待审申请可以撤销”实现。撤销后关闭所有相关待办。
- 被驳回后可参考原申请重新提交，形成新编号并保留原记录。
- 已批准申请的取消、续假和变更尚未确定为一期独立业务，不得通过修改数据库替代；如需要应另定流程。

### 4.2 审批规则与流程配置

- 按请假类型、请假时长配置审批路线，必要时允许按组织、离校或外宿条件进一步匹配。
- 节点支持指定人员或指定角色。按角色处理时结合学生组织解析实际审批人。
- 支持一级或多级顺序审批，当前节点通过后进入下一节点；任一节点驳回则结束该申请的审批。
- 匹配规则应有明确优先级和互斥处理，避免同一申请匹配多个不确定流程。
- 找不到流程或审批人时返回明确错误，不自动批准；已在途流程的审批人失效时向管理员暴露异常待办。
- 保存申请使用的流程版本、节点和审批人。管理员调整流程不静默改写已提交申请的审批历史。
- 审批时显示学生资料、申请内容、附件、前序意见及相关历史记录。
- 支持通过、驳回和填写意见；驳回意见必填。
- 节点操作必须校验当前状态、当前节点、操作人及管理范围。
- 重复点击或同时审批只能产生一次有效状态变化。

### 4.3 批量审批

- 审批人可选择多个属于本人当前待办的申请，批量通过或驳回。
- 执行前展示数量和关键内容，支持填写共同意见。
- 每条申请单独校验，返回成功、失败或已被处理的结果及原因。
- 为每条申请保存审批记录，不能只记录一次批量操作而丢失个人业务历史。

## 5. 定位打卡与销假管理

### 5.1 学生发起销假

- 仅对已批准且尚未正式销假的请假申请发起销假。
- 手机端主动获取定位，展示定位状态和校区核验结果，由学生提交销假申请。
- 后端根据所属校区电子围栏核验坐标，不能只相信前端返回的“在校内”结果。
- 保存坐标、定位精度、定位采集时间、服务器接收时间、校区及围栏核验结果。
- 围栏支持校区实际需要的圆形或多边形范围；边界容差和最低精度要求可配置，统一围栏与定位坐标系。
- 提交时间以服务器时间为业务依据，不使用手机自行修改的时间决定是否逾期。
- 不持续采集学生位置，只在主动打卡时采集必要信息。
- 已有待审销假申请时禁止重复生成同类待办；失败重试保留有效业务的一致性。
- 允许提前返校提交销假，记录实际打卡时间和批准的请假区间。

### 5.2 中队长确认

- 销假待办分配给对应中队长，展示请假时间、打卡时间、定位及精度、核验结果、是否逾期等信息。
- 中队长支持确认、驳回及批量确认，驳回须填写理由。
- 确认后更新销假状态、业务在校状态和相关提醒，保存确认人及确认时间。
- 驳回后学生可重新打卡申请，保留各次提交及审核记录。
- 学生提交打卡与中队长确认是两个事件。提交后为“销假待确认”，不能提前显示为“已销假”。

### 5.3 异常处理

- 定位授权被拒绝、超时、精度不足、设备不支持或不在围栏内时，显示具体原因及处理入口。
- 默认围栏校验通过才允许正常定位销假；确需定位异常人工核验时提供单独入口，由有权限人员审核并填写原因，标记为人工核验。
- 浏览器位置可能被伪造，定位作为审核依据之一，不宣称能够完全防止位置作弊。
- 多校区学生按其有效所属校区核验；允许跨校区销假与否由学校规则配置。

## 6. 超时预警、通知与待办

### 6.1 预警规则

- 以已批准请假的结束时间为基准，设置宽限时间、提醒层级和升级间隔。
- 可配置结束后提醒中队长，超过指定小时后再提醒大队长或其他角色；具体阈值由学校提供，不硬编码为正式校规。
- 区分“未提交销假”和“已经提交但待中队长确认”，不能将后者直接等同于未返校。
- 请假被驳回、撤销或已完成销假后，不再产生对应超时提醒。
- 服务重启后恢复检查，避免遗漏已到期记录；同一规则和申请的提醒防止重复生成。

### 6.2 一期通知

- 通知事件：新审批待办、节点流转、最终批准、驳回、撤销、销假待确认、销假结果、超时和异常待办。
- 手机端与电脑端提供消息中心、未读数量、待办列表及跳转到申请详情。
- 用户可以查看消息和标记已读，提醒仅展示权限范围内的数据。
- 一期站内消息不承诺用户关闭网页后仍收到主动推送；企业微信、短信和其他外部通知属于后续接口范围。
- 外部通知将来失败时，不应回滚已经完成的审批或销假业务，应独立记录失败并重试。

## 7. 查询、报表与统计

### 7.1 查询和导出

- 学生查询个人请假及销假记录；管理人员按授权范围查询。
- 支持按学号、姓名、组织、专业、班级、校区、请假类型、申请状态、时间区间、离校、外宿及逾期情况筛选。
- 支持组合筛选、排序、分页，查看完整申请、审批、打卡、销假和提醒历史。
- 支持导出当前筛选范围及当月请假明细，字段包括学生及组织信息、事由、起止时间、时长、审批结果、审批人和意见、销假状态和时间等。
- 导出与页面查询使用相同权限规则；用户不能通过导出查看超出范围的数据。

### 7.2 统计维度与口径

- 班级、中队、系部、院系及全校统计：学生基数、请假人数、申请次数、请假总时长、当前请假人数、待销假人数及逾期人数。
- 学生个人统计：按学年、学期或时间范围汇总次数、类型、时长和逾期情况。
- 按日、周或月展示趋势，按请假类型展示分布。
- 支持配置频繁请假或超过时长阈值的标记，作为管理提醒，不能自动生成处分结果。
- 请假人数按学生去重，请假次数按申请计数；批准申请才计入有效请假统计，驳回和撤销单独统计。
- 跨月申请按查询区间重叠时长统计；总批准时长和实际打卡时长分别保存、分别命名，避免混用。
- 当前请假人数按“已批准、当前在批准区间内且未完成销假”计算；逾期未销假单独列示。
- 已提交销假待确认与尚未提交销假分别展示；报表标明统计时间及口径。
- 历史组织报表默认采用申请发生时的组织快照；在读人数等当前基数采用统计时的有效学生资料并明确标注。

## 8. 页面与主要业务状态

### 8.1 手机端页面

- 登录、首次密码设置及个人资料。
- 学生首页：新建请假、我的请假、审批进度、销假打卡、消息中心。
- 管理人员首页：请假待办、申请详情、批量审批、销假待办、超时名单和范围内查询统计。
- 表单适配手机，支持拍照或相册上传证明材料；状态、失败原因和提交结果清楚可见。

### 8.2 电脑端页面

- 工作台：待办数量、请假概况、销假概况和超时提醒。
- 账号、角色、管理范围、组织、专业、班级、校区及学生导入管理。
- 请假流程、审批规则、围栏和预警规则配置。
- 请假记录、审批待办、销假记录、预警名单、查询报表和导出。
- 系统参数、操作日志、导入日志及异常待办。

### 8.3 业务状态

请假审批状态与销假状态分别保存，避免一个字段同时承担所有含义。

| 业务 | 状态 | 转换规则 |
| --- | --- | --- |
| 请假审批 | 待审批 | 提交并进入首个节点 |
| 请假审批 | 审批中 | 已有节点通过，后续节点尚未完成 |
| 请假审批 | 已批准 | 最后一个节点通过 |
| 请假审批 | 已驳回 | 任一节点驳回 |
| 请假审批 | 已撤销 | 在允许撤销的状态由学生撤销 |
| 销假 | 未申请 | 已批准请假尚未提交销假 |
| 销假 | 待确认 | 学生提交定位或异常人工核验申请 |
| 销假 | 已驳回 | 中队长驳回，可重新提交 |
| 销假 | 已销假 | 中队长确认完成 |

“未开始”“请假中”“逾期未销假”可由审批状态、销假状态和当前时间计算。超时不会自动将申请改成已销假，也不会自动证明学生实际未返校。

## 9. 数据、附件和运行质量要求

### 9.1 核心数据对象

账号、角色、权限、用户角色、管理范围、组织、专业、班级、校区、学生资料、学生组织变更、导入批次、请假类型、流程配置及版本、请假申请、申请流程节点、审批记录、附件、销假申请、打卡记录、销假审核记录、预警规则、预警记录、站内通知及操作日志。

- 请假记录关联学生内部标识和学号快照，保留当时组织及流程信息。
- 附件保存文件元数据及受控存储位置，数据库保存关联信息。
- 审批、销假和权限变更日志保存操作人、时间、对象、结果及必要原因，普通用户不可修改。
- 核心业务使用事务保证一致性，失败不能产生“已批准但节点未完成”等矛盾状态。

### 9.2 安全与可靠性

- 后端完成身份认证、角色权限和数据范围校验，保护导出及附件访问。
- 附件限制类型与大小，使用安全文件名和受控下载接口，不公开整目录。
- 配置和日志不输出明文密码或完整凭证；数据库账号采用适当权限。
- 系统时间统一按北京时间展示，提醒和统计采用一致的时区口径。
- 提供数据库和附件备份、恢复步骤，恢复后业务记录与附件能够对应。
- 用户看到清楚的校验和错误提示；开发日志保留定位问题所需信息。
- 具体并发用户数、响应时间和容量目标待学生规模及服务器条件明确后确定，不能在无测试的情况下承诺数值。

## 10. 本地运行要求

推荐技术方向：Vue 3 + TypeScript 前端，电脑端使用 Element Plus、手机端使用 Vant；Java Spring Boot 后端；独立 MySQL 数据库。先采用一个后端应用，内部划分业务模块。

- 在本地电脑建立单独的开发数据库，不依赖教务、统一登录、门禁、企业微信或学校服务器。
- 提供数据库初始化或迁移脚本、基础角色、示例组织、各角色测试账号、虚构学生及可配置审批规则。
- 示例密码仅用于开发环境，通过明确方式初始化；正式导入数据时能够替换示例资料。
- 提供本地环境配置样例，包含数据库连接、附件目录、服务端口及前端接口地址。
- 提供前端与后端启动步骤、停止步骤、访问地址和常见问题说明。
- 本地附件保存在可配置目录，数据库持久保存；重启后账号、申请和附件仍可访问。
- 本机浏览器访问 localhost 可用于定位测试；手机访问电脑的局域网 IP 时，不能假定普通 HTTP 也能定位，应配置手机信任的 HTTPS 开发入口。
- 手机测试时配置网络连通、防火墙及接口地址。手机中的 localhost 指向手机自身，不能作为电脑后台的访问地址。
- 开发测试可以设置模拟定位入口，但必须明确标记，只在开发环境启用，正式环境关闭。
- 本地运行不要求公网域名或公网 IP；定位成功与否仍需在实际设备上验证。
- 后续部署学校服务器时更换环境配置，并完成域名、可信 HTTPS、访问方式、备份和运维配置。

## 11. 一期验收场景

1. 导入学生文件后正确新增或更新资料；重复导入不重复建号，错误行能够定位。
2. 学生、各级审批人和管理员登录后看到对应功能；越权访问、下载和导出被后端拒绝。
3. 不同请假类型和时长按配置进入正确路线；无流程或无审批人时有明确提示。
4. 多级审批按顺序流转，驳回、撤销及时关闭待办；批量操作逐条返回结果。
5. 学生能够在手机上申请、查看进度、上传附件，管理人员能够在手机上审批。
6. 已批准申请能够在允许校区打卡；校外、定位失败或精度不足时按异常规则处理。
7. 打卡后显示销假待确认，中队长确认后才显示已销假；重复提交和并发处理不产生重复结果。
8. 到期未提交销假、已提交待确认分别显示；超时规则产生正确提醒，完成销假后停止提醒。
9. 查询、统计和导出遵守管理范围，去重、跨月和批准时长口径一致。
10. 学生调班、审批人停用及流程修改不丢失历史记录，也不留下不可见的异常待办。
11. 本地重启后数据持久保留，提醒检查恢复；数据库及附件备份能够恢复。
12. 手机和电脑页面在目标浏览器可用，实际手机定位与 HTTPS 环境验证通过。

## 12. 编码前需要最终确定的学校规则

- 实际组织层级，以及学生、班级与中队长、大队长的对应关系。
- 请假类型、时长算法、分级审批阈值、是否允许外宿及事后补假。
- 销假围栏、精度要求、跨校区规则、人工核验权限及销假驳回后的处理。
- 超时宽限期、提醒对象、升级间隔及频繁请假预警阈值。
- 实际教务导入文件、字段、学籍状态取值及账号初始化方式。
- 是否在一期增加批准后取消、续假、代理审批或多人会签。
- 学生规模、管理人员规模、目标手机浏览器和学校服务器限制。
