### 最终确定的核心原则

1. 独立网页系统和独立账号，学生通过 Excel/CSV 导入；不直接连接教务数据库。
2. 桌面、手机浏览器和微信内置浏览器均支持，正式数据和证明材料留在学校服务器；当前先在 Windows 本地运行。
3. 服务端严格控制用户身份、组织授权、数据范围、状态变更和审计，页面隐藏不等于权限控制。
4. 请假按**实际起止时间差**计算，以 12 小时为半天单位、不足半天向上取整，审批流程及其天数区间由管理员自定义。
5. 每名学生最多有一条未结束的普通请假链；关联续假最多**成功一次**，按累计实际时长折算天数匹配流程。
6. 普通请假及续假无论类型均**强制上传证明**；允许说明原因补假、符合条件时撤销、未出发取消审核及取消申请撤回。
7. 只有离校请假需要返校销假：请假开始后、未逾期、定位在任一有效校区内时**自动销假**；定位异常或逾期由中队长人工审核。
8. 在途待办遇学生调班或负责人调整，必须自动交接并留痕；已完成历史不被改写。
9. 一期只有站内消息及待办，微信主动推送、统一认证、短信和门禁对接不构成依赖。
10. 本地运行坚持单仓库 Next.js + MySQL + 同仓库任务进程，提供迁移、初始化、启动、停止、备份及恢复脚本。

# 第一部分：最终功能与技术需求

## 1. 已确认的项目目标

1. 建设独立的学生请假管理系统，独立数据库、独立账号体系。
2. 从教务提供的 Excel/CSV 文件导入学生资料，在本系统建立账号，不直接连接教务数据库。
3. 中队长、大队长、学工处、院领导等管理人员也在本系统维护账号及权限。
4. 提供电脑、平板和手机可访问的响应式网页，不开发独立安装的手机 App。
5. 仅离校请假需要销假：请假已开始、未超过有效批准返校时间，且在任一有效校区定位通过时自动销假；定位异常或逾期转所属中队长人工审核。非离校请假到期结束，不要求定位销假。
6. 学生总数不到 8000 人，每年级约 3000 人；日常预计同时操作人数不高，需考虑集中请假和集中返校高峰。
7. 目前先完成本地开发运行，不以学校服务器、域名或任何外部账号为启动前提。
8. 后续正式运行时，学生资料、业务记录和附件全部保存在学校服务器。
9. 主要由项目负责人配合 AI 维护，优先减少独立服务数量，提供清楚的配置说明和启动脚本。
10. 中队长对应具体分配的班主任，负责指定班级；大队长管理管理员指定的中队长及其管理范围；院领导负责指定系部。人员上下级、组织层级、管理板块和范围均由管理员配置并可动态调整。
11. 请假时长与审批流程的对应关系由管理员自主配置，不将固定天数阈值或审批层级写死在代码中。
12. 学生调班或中队长、大队长、系部负责领导等管理关系变化时，受影响的未处理普通请假、续假节点、取消审核及人工销假待办均按新关系自动交接并留痕；已完成记录保留原处理人。
13. 请假按精确起止时间的实际时长计算，12 小时计 0.5 天、24 小时计 1 天；不足 12 小时的部分向上取整至下一个 0.5 天档位。例如 10 月 17 日 16:00 至 10 月 18 日 10:00，实际 18 小时，计 1 天。
14. 学生仅能在尚无人审批时自行撤销；已有节点完成审批后不能自行撤销。
15. 一期支持关联原申请的续假，每段请假最多成功续假一次；被驳回或撤销不占成功次数，可重新申请。续假单独提交并重新审批，不直接改写原批准记录。
16. 导入的新学生账号使用管理员设置的统一初始密码，首次登录必须修改密码后才能使用业务功能。
17. 续假按原假与续假累计总天数匹配审批流程；原假 2 天、新增 3 天时，按 5 天匹配。
18. 允许超过原返校截止后申请续假，须标记逾期并说明原因。续假批准前仍按当前有效批准截止检查未归，不因提交而暂停检查。
19. 已批准但尚未出发的请假，学生可申请取消；即使请假开始时间已到，也允许说明未出发情况，由所属中队长核实审核并留痕。
20. 普通请假与续假的所有请假类型均必须上传证明材料，不能作为选填。
21. 手机普通浏览器和微信内置浏览器均为一期支持入口，均需验证登录、申请、附件、审批及销假体验。
22. 多校区均可作为返校地点，定位核验遍历允许销假的有效校区范围，不限制只能回到学生所属校区。
23. 因定位失败进入人工销假待审后，可重新打卡；重新定位通过且未逾期时自动销假，关闭原人工待办并保留全过程记录。
24. 请假尚未开始时不能打卡销假，只提供取消申请入口，由中队长审核。
25. 允许补交已经开始或结束的普通请假，必须标记补假并说明原因。
26. 同一学生不能同时保留多条未结束普通请假，即使时间不重叠；上一条结束、销假或其他有效终止后才能再申请。续假属于原请假链，不是新建另一条普通请假。
27. 一期仅提供站内消息及待办，关闭网页后不承诺手机主动推送；微信主动通知、短信等留到后续，不作为本地开发前提。
28. 人工销假待审核期间不能申请续假，须先处理或结束现有人工销假申请；已完成销假的请假不能再续假。
29. 已批准请假的取消申请尚未审核时，学生可撤回该取消申请，原批准继续有效；撤回与审核并发只能有一个合法结果。

### 1.1 V2.8 已确认规则摘要

- 未逾期且定位核验通过的打卡自动销假；定位异常或逾期返校进入中队长审核。
- 管理关系采用管理员动态分配，不能仅根据角色名称推定固定上下级。
- 请假审批按管理员配置的折算天数区间选择流程；具体阈值由管理员配置。
- 学生调班及各管理层负责人调整时，未处理待办均按新关系自动交接，已完成历史不改写。
- 未经任何节点审批的申请可以本人撤销；续假纳入一期并关联原申请重新审批。
- 学生使用管理员统一设置的初始密码，首次登录强制修改。
- 每段请假最多成功续假一次，被驳回或撤销可重提；按累计总天数重新审批，逾期申请需说明，批准前仍按旧截止检查未归。
- 已批准但未出发的请假支持学生申请取消、中队长审核；所有请假和续假类型必传证明。
- 请假已开始但实际未出发仍可申请取消，由中队长核实；普通手机浏览器和微信内置浏览器均需支持。
- 仅离校请假需要销假，任一有效校区定位均可；非离校请假到期结束，不产生返校销假待办。
- 定位失败的人工待审申请可由按时成功重打卡自动结束，原待办关闭并留痕；逾期仍须人工审核。
- 未开始请假不能提前销假；普通补假允许但必须说明；普通请假采取一条未结束链限制，不因时间不重叠而放行多条。
- 一期只做站内提醒和待办，主动推送后续扩展。
- 人工销假待审时不能申请续假；取消申请待审时可以由本人撤回，原请假继续有效。
- 本版本取代 V2.0 的所有销假均需人工确认，以及 V2.1 尚未明确逾期和计天口径的规则。

## 4. 架构与本地运行原则

### 4.1 进程和数据

- 一个 Next.js 应用处理页面、认证及业务接口。
- 一个同仓库后台任务进程检查超时记录；与网页共用配置、数据模型和业务规则，不另起一套后台系统。
- 一个本地 MySQL 服务保存数据。
- 一个可配置附件目录保存文件；应用更新、进程重启不删除文件。
- 日常启动脚本统一管理网页和任务进程，避免要求零经验用户手动维护多个终端。
- 网页关闭后，只要电脑、数据库和后台任务仍运行，超时检查继续执行。
- 电脑关机、休眠或任务进程退出期间不承诺持续提醒；恢复运行后补查到期记录。

## 5. 用户角色与权限

### 5.1 基础角色

| 角色 | 主要能力 | 默认数据边界 |
| --- | --- | --- |
| 学生 | 申请请假及续假、查看进度、撤销允许撤销的申请、申请批准后取消、提交销假、查个人统计 | 本人 |
| 中队长 | 班主任身份，负责请假、批准后取消及异常销假审核、查询统计和预警 | 管理员指定的班级或中队 |
| 大队长 | 按流程审批、查看统计、处理升级预警 | 管理员指定的中队长及其有效管理范围，另有授权则按明确范围执行 |
| 学工处人员 | 按授权审批、查询统计及预警 | 指定组织或全校 |
| 分管院领导 | 按流程审批、查看汇总及预警 | 管理员指定的系部；全校范围需要额外明确授权 |
| 系统管理员 | 账号、权限、组织、流程、围栏、参数、日志及异常管理 | 配置权限；业务操作权限另行授权 |

### 5.2 权限规则

- 一个用户可拥有多个角色，并可负责多个组织；界面支持明确当前操作身份。
- 角色决定“能做什么”，管理范围决定“能管理哪些学生及记录”。
- 管理员可维护“中队长负责哪些班级”“大队长管理哪些中队长”“院领导负责哪些系部”及人员上下级关系，提供新增、调整、解除和关系查询。
- 人员管理关系与组织树分别记录，解析审批人、统计范围和预警对象时使用配置，不假定一个角色只能属于一个固定组织层级。
- 学生调班或管理关系变更后及时更新业务路由及有效数据范围，记录调整人、时间和前后关系；中队长、大队长、系部负责领导等相关职责的未处理普通请假及续假节点、取消审核和人工销假待办，全部按新关系自动交接，不改写已完成历史。
- 自动交接保存原处理人、新处理人、操作者、原因、时间和关联事项；关闭原待办、建立或更新新待办，防止遗漏或重复。
- 原负责人仅凭旧待办或已打开页面不能继续操作；若有其他独立有效授权，仍按当前权限判断。交接与处理并发时保证最终状态一致，已处理的事项不重新开放。
- 当前待审节点更新实际处理对象，尚未激活的相关角色节点在激活前校验新管理关系和有效负责人；流程版本及节点顺序保留，已完成节点不重新审批。
- 调班不追溯改写原申请的学生组织快照，历史报表仍按当时归属；当前待办权限及处理对象按新关系解析，不能因历史快照把事项继续交给旧负责人。
- 新关系无法解析有效审批人时生成明确异常待办并提示管理员修复，不自动通过、跳过或交给无权限人员；不能静默丢失原事项。
- 配置管理关系时防止循环管理、无效对象及意外扩大授权范围。
- 权限必须覆盖列表、详情、接口、服务端操作、统计、导出和附件下载，不只隐藏菜单或拦截页面。
- 学生不能通过修改申请编号、附件编号等查看或操作他人数据。
- 审批人必须同时符合当前审批节点、账号有效状态和授权范围。
- 管理员不自动拥有业务审批或代审批权；无明确权限时不能绕过节点。
- 原始审批记录不可由普通用户修改。确需纠正业务数据的功能须有明确授权、原因及前后状态审计。
- 多角色人员是否允许审批自己的申请、同一人在多个节点如何处理，列为待确认规则；演示环境默认禁止自审、不自动跳过节点。
- 组织层级和名称可配置，不把“院系、大队、中队、班级”假定为所有学校都相同的固定结构。

## 6. 基础资料与学生导入

### 6.1 组织、专业、班级、校区（V3.2 最终确认）

**确认采用“学校 → 系部 → 专业 → 年级 → 班级 → 学生”的学籍归属结构。** 这是学生组织归属与按组织统计的基础；“中队长—大队长”等人员管理关系为独立的授权关系，不强行塞入该树形层级。

```text
学校
├── 系部 A（管理员创建）
│   ├── 专业 A1（管理员指定唯一所属系部）
│   │   ├── 年级 → 班级 → 学生
│   │   └── 年级 → 班级 → 学生
│   └── 专业 A2
│       └── 年级 → 班级 → 学生
└── 系部 B（管理员创建）
    └── 专业 B1
        └── 年级 → 班级 → 学生
```

以上仅为结构示意，**不预置、不写死任何真实系部或专业名称**。学校实际的系部、专业、年级、班级及对应关系均由管理员在系统后台手动添加、编辑、启停与调整，无须重新部署或改代码。用户提供的图片展示了两个系部各自管理多个专业的形式，仅用于确认类似的组织结构；图片中的具体名称不作为初始化的正式数据。

**组织配置约束：**

1. 一个系部可管理零个、一个或多个专业；**每个有效专业在同一时间必须且只能归属一个系部**，禁止同时归属多个系部。专业不能被重复挂载到不同系部，专业的有效归属应使用明确外键和数据库约束保障。
2. 专业由管理员维护编码、名称、所属系部、状态与变更历史；校内出现同名专业时应通过专业编码等稳定标识消歧，避免仅凭显示名称关联。
3. 每个班级明确其专业与年级，学生明确其班级；系统应按有效关系获得所属专业和系部，并在申请时保存组织快照。独立校区属性可与该层级并存，不把校区默认等同于系部。
4. 管理后台提供**系部管理、专业管理、专业归属设置、年级班级管理**的新增、编辑、停用、搜索和树形查看；选择系部后可查看其专业，选择专业后可查看其年级、班级和学生，提供必要的归属数量与异常提示。
5. 调整专业所属系部时，管理员先看到受影响的班级、学生、当前负责人授权范围和未处理事项，再确认变更；变更后按新关系重新解析当前数据访问权限及相关待办。无法匹配合法新负责人时形成管理员异常待办，不允许静默漏单或自动批准。
6. **组织归属与审批授权分别配置。** 系部下有某专业，不等于每名系部工作人员天然拥有审批权；审批操作仍须满足角色、流程节点及当前有效管理范围。院领导可通过管理员授权负责某系部，其管理范围根据当前有效专业归属解析。
7. 历史申请保留提交时的系部、专业、年级、班级快照；调整专业归属不回写已完成审批与历史统计快照。当前待办和当前管理查询按照新关系执行，统计界面须明确按历史归属还是当前归属查看。
8. 系部或专业已被班级、学生或历史业务引用时，不直接物理删除，采用停用及保留历史关联；停用前应提示受影响对象，并对待处理业务落实负责人。
9. Excel/CSV 学生导入时，按专业唯一编码及系部归属检查组合关系；导入文件中的系部与系统专业归属矛盾时须报错或由管理员明确纠正，不能隐式新建不受控系部或将学生挂到其他专业。
10. 中队长负责具体班级、大队长管理指定中队长及其范围、院领导负责指定系部的人员关联继续由管理员单独配置，允许按校方管理制度调整，不能仅凭组织树推定所有行政上下级。

**一期交付要求：** 组织管理必须为真实可保存、可编辑、可权限校验、可关联导入和请假审批的功能，而非写死的演示页面或静态结构图。允许初始化虚构演示数据，但正式运行前可在后台清晰区分、调整或替换。

### 6.2 学生资料

必备字段：学号、姓名、组织、专业、年级、班级或中队、所属校区、学籍状态、账号状态。联系方式等额外字段按业务需要收集。

- 学号按字符串保存，保留前导零，不按数字计算或自动转科学计数法。
- 支持学生检索、资料维护、调班、转专业、学籍变更和账号停用。
- 学籍状态、账号状态、业务请假状态分开，不相互替代。
- 历史申请保留申请时的学生与组织快照。
- 学生调班、班级或中队长归属调整，以及大队长或院领导变更时，受影响的未处理普通请假、续假、取消和人工销假待办自动交给新关系对应人员并留痕，不产生无人处理的隐藏记录。
- 业务在校状态由是否离校、请假及销假记录推算，不作为实际门禁出入事实；未来已批准请假不立即标为已经离校，非离校请假不标为离校或未归。

### 6.3 导入流程

1. 下载模板并查看字段说明。
2. 上传 Excel 或 CSV，选择并核对工作表或字段映射。
3. 预校验，展示总行数、新增、更新、不变及错误行。
4. 用户确认导入范围后执行。
5. 展示逐行或分组结果，提供错误报告下载，并记录导入批次及操作日志。

校验与执行要求：

- 以学号唯一识别学生；检查重复学号、必填项、字段长度、日期及组织归属。
- 未知系部、专业、班级或校区必须报出或提供明确的建立及匹配步骤，不能静默挂到错误组织；专业与系部归属不一致、一个专业存在多个当前有效系部归属时必须拒绝导入并给出错误行。
- 批内重复学号视为冲突，不按不透明的最后一行覆盖。
- 重复导入不重复建号，不重置已有密码，不覆盖历史业务。
- 管理员在导入新账号时设置本批次统一初始密码，仅用于新建账号；更新已有学生资料不覆盖其密码或首次修改状态。
- 不因文件缺少某学生而自动停用或删除该学生。
- 用户可选择仅导入通过校验的行，错误行跳过；正式写入仍需复核数据状态。
- 一次导入中单个学生资料、账号及组织关联保持一致，失败报告说明影响范围。
- 同一导入批次重复确认应防止重复执行；文件和错误报告的访问遵守权限。

## 7. 账号、密码和会话

- 学生使用学号登录；管理人员使用分配的用户名登录，账号标识保证唯一。
- 账号仅通过管理员、导入或受控初始化建立，不开放公众注册；关闭认证组件未使用的开放注册入口。
- 不要求学生具备真实邮箱、接收短信或使用外部身份服务才能登录；内部认证字段由实现适配，不伪称已完成邮箱验证。
- 新建学生账号使用管理员设置的统一初始密码，管理员可在导入前设置并按学校渠道告知学生；不默认使用学号、生日等个人资料推导密码。
- 首次登录验证成功后只开放改密、必要的本人资料读取及退出入口；修改成功前不得访问或调用请假、审批、销假等业务接口，不能只在页面提示。
- 首次修改后的密码不得与初始密码相同，修改成功后更新强制改密标记并处理原受限会话；由认证流程生成正常可用会话。
- 导入批次变更初始密码不影响已有账号；同一初始密码由认证机制为各账号分别生成安全哈希，不复用一个裸密码哈希冒充全部账号的独立凭证。
- 开发实现默认每次新增导入由管理员输入初始密码，服务端仅在创建凭证时使用，不把可读取的统一明文密码长期保存在设置表中。
- 首次密码设置与账号激活使用受控流程；管理员重置后同样要求本人修改密码。
- 不沿用或索取教务系统密码，不保存明文密码；使用认证库支持的安全密码哈希机制。
- 提供登录、退出、修改密码、管理员重置、账号启停和登录失败限制。
- 使用数据库支持的可撤销会话，浏览器通过受保护 Cookie 维持登录。
- 停用账号、重置密码或注销全部设备后，旧会话应在后续受保护请求时失效。
- 权限调整后及时使用有效权限执行敏感操作，不能长期相信旧会话中的角色快照。
- 正式 HTTPS 环境使用 Secure、HttpOnly 及适当 SameSite 设置；开发 HTTP 的配置与正式配置分开。
- 修改业务的请求需要认证、权限与必要的跨站请求防护。
- 个人中心展示必要个人资料及密码修改入口；学生不自行更改学号或组织归属。
- 未接入短信、邮件前，忘记密码由管理员核验身份后重置。

## 8. 学生请假申请

### 8.1 申请字段

| 字段 | 要求 |
| --- | --- |
| 申请编号 | 系统生成，唯一且可查询 |
| 学生与组织 | 从登录身份和有效学生资料读取 |
| 请假类型 | 从启用的配置选择 |
| 请假事由 | 必填，限制长度 |
| 开始、结束时间 | 必填，按北京时间明确展示 |
| 请假时长 | 后端按实际时长折算为 0.5 天的倍数，前端同步预览实际小时和折算天数 |
| 是否离校 | 必填；后端据此确定是否需要销假，非离校不进入返校销假流程 |
| 是否外宿 | 必填，并校验与离校选项的业务关系 |
| 外出地点、联系电话 | 是否必填由规则确定 |
| 证明附件 | 所有类型的普通请假和续假均必填，至少关联一份上传成功且通过校验的证明，允许多份 |
| 预计审批路线 | 提交前展示可解析的节点及处理对象 |

### 8.2 业务校验

- 结束时间必须晚于开始时间。
- 审批用天数按精确起止时刻之差计算，1 天 = 24 小时，0.5 天 = 12 小时；实际时长大于 0 的申请按 12 小时为一档向上取整。公式：折算天数 = ceil(实际分钟数 / 720) × 0.5。不得按起止日期包含的自然日计算。
- 10 月 17 日 16:00 至 10 月 18 日 10:00，实际 18 小时，审批折算为 1 天；10 月 17 日 08:00 至当日 20:00，实际 12 小时，计 0.5 天；25 小时计 1.5 天。跨日、跨月、跨年均仅计算实际时长。
- 起止时间精确到分钟并按统一时区处理，用于返校截止、逾期和时间冲突；跨越零点不会额外增加天数，节假日不默认扣除。页面同时展示实际小时数和向上取整后的审批天数，严格禁止零时长或结束不晚于开始。
- 后端完成必填、格式、长度、时间和附件归属校验。
- 所有类型均强制检查证明，不允许通过省略字段、上传失败或只填写文件名绕过；续假同样检查有效附件关联。管理员可配置文件类型、数量和大小，但一期不提供关闭证明必填的选项。
- 同一学生最多存在一条未结束的普通请假链：包含待审批、审批中、已批准未开始、进行中，以及离校到期未销假的有效申请。即使新申请时间不重叠，仍应阻止并指向需先处理的原申请。
- 已驳回、本人按规则撤销、取消审核通过、离校已销假及非离校已经到期结束的请假不占该限制；取消申请仅待审时仍占用。状态判断必须在后端执行，并发创建不得绕过。
- 检查有效普通申请时间重叠，避免同一时间重复请假；驳回和撤销记录不阻止重新申请。续假与所关联原申请按连续请假链单独校验，不能被普通申请重叠规则误拦截，但仍需检查与其他请假链的冲突。
- 精确相邻的两个时间区间不默认视为重叠，统一采用明确的起止边界口径。
- 已确认允许普通补假：开始时间早于提交时间时由后端识别，要求补假标记和补假原因，覆盖已开始未结束及已结束两种情况；不允许客户端隐瞒补假性质。
- 补假仍需证明、正常流程审批、唯一未结束链及冲突校验，不能补写或倒签审批时间。批准时已超过结束时间的离校补假仍需人工销假；非离校补假按实际时间结束，不生成未归预警。
- 提前申请上限和最长请假限制可后续配置；未完成离校销假前不能再提交普通请假，可按既定规则关联续假。
- 保存时长计算规则及必要结果，避免之后改规则导致旧申请时长变化。
- 提交成功后不能直接编辑在途申请内容。
- 重复点击或网络重试不产生多个有效申请，后端设置幂等及必要事务保护。
- 输入或校验失败时保留已填写内容并提示具体原因。


### 8.2.1 请假时长折算示例（V3.1 修订）

| 实际时长 | 审批折算天数 | 说明 |
| --- | --- | --- |
| 1 分钟 | 0.5 天 | 不足半天向上取整 |
| 6 小时 | 0.5 天 | 不足 12 小时 |
| 12 小时 | 0.5 天 | 刚好半天 |
| 12 小时 1 分钟 | 1 天 | 超过半天进入下一档 |
| 18 小时 | 1 天 | 12～24 小时之间 |
| 24 小时 | 1 天 | 刚好一天 |
| 24 小时 1 分钟 | 1.5 天 | 超过一天进入下一档 |
| 36 小时 | 1.5 天 | 刚好一天半 |
| 48 小时 | 2 天 | 刚好两天 |

**续假折算重要原则：**按原开始时间至拟延长截止时间的总时长一次性进位，不把原批准的进位天数与新增时段进位天数相加。例如原始 10 小时计 0.5 天，续加 3 小时后累计 13 小时，应计 1 天，而非分别计 0.5 + 0.5 后误用相同结果的算法（在其他时长组合下可产生差异）。

**时区和精度：**时间储存采用 UTC，展示使用北京时间（Asia/Shanghai），后端按真实经过分钟计算；夏令时或部署时区变化不能改变同一组时间戳计算结果。审批规则区间允许 0.5 天粒度，首尾边界无重叠、无空档。

### 8.3 撤销、驳回与再次申请

- 已确认仅允许“尚无任何节点完成审批”的待审批申请由本人撤销；已有任何节点完成审批后，不再允许自行撤销。
- 撤销与审批并发发生时，只允许一个合法操作成功，并返回最新状态。
- 撤销后关闭相关待办，保留原记录。
- 驳回必须给出意见，学生可参考原内容创建新申请，新旧记录可追溯。
- 已批准申请不提供直接覆盖、删除或改时间的入口；续假及批准后取消使用独立关联流程，其他内容变更仍待另定规则。

### 8.4 关联续假与重新审批

- 学生从本人已批准、未取消的原申请进入续假：离校请假必须尚未销假；非离校按已确认的逾期续假规则处理。系统关联同一连续请假链，生成新的续假编号。
- 续假填写新的返校时间、续假理由和所需附件，展示原批准区间、当前有效截止、新截止及审批所用天数。
- 新截止必须晚于当前有效批准截止；同一请假链一次只允许一条有效待审续假，防止并行延长覆盖。
- 续假走独立审批实例，保存流程版本、节点、意见和结果；不能复用原单已通过节点来跳过重新审批。
- 已确认按累计总天数匹配流程：以原申请精确开始时刻到本次申请新截止时刻的总实际时长，按 12 小时档位向上取整为累计折算天数；例如原区间 48 小时、新增 72 小时，累计 120 小时，按 5 天匹配，而非只按新增时长匹配。
- 允许在当前有效批准截止之后提交续假，必须填写逾期续假原因，并保存提交时有效截止、提交时间、逾期标记及必要时长。
- 续假尚未最终批准不改变有效返校截止，未归检查与预警继续按旧截止执行；提交续假不自动暂停提醒，也不提前放宽销假时限。
- 未归检查仅适用于离校请假；非离校请假到期不产生未归提醒。非离校逾期续假仍保留提交时间和逾期续假标记，不能将其误当返校逾期。
- 续假批准后产生新的有效截止及生效记录，保留原申请、历次批准区间、续假单及完整审批历史；后续打卡、逾期判断和任务扫描读取最新有效批准截止。
- 本文销假及预警中的“批准结束时间”“批准返校时间”均指请假链当前有效批准截止；原始申请结束时间作为历史字段保留，不与有效截止混淆。
- 续假驳回或按撤销规则撤销，只结束该续假，不撤销原已批准请假，也不延长有效截止。
- 普通申请和续假分别计数，持续请假的人数及有效时段按链合并，避免批准原单和续假后重复计算学生或重叠日期。
- 累计匹配天数应先合并请假链的精确时间区间、求出总实际分钟数，再统一向上取整至 0.5 天；新增实际时长按新旧截止精确计算，不重复计算交接时刻。严禁先分别进位后相加造成虚增；流程展示累计实际小时和折算天数。
- 续假审批、原申请销假和其他状态变化并发时必须核验整条请假链；已经完成销假的链不能被迟到的续假审批再次延长或重新打开。
- 续假必须与其他请假链及一条未结束链限制协调：不能通过给已到期非离校旧单续假，重新制造与另一条当前有效请假并存的状态。
- 已确认每段请假最多成功续假一次。续假最终批准才占用成功次数，驳回或撤销不占用，可创建新续假申请重提并保留前次记录。
- 一条续假待审期间不能再建另一条待审续假；获批后不再提供第二次成功延长入口，后端校验成功次数。并发批准不得产生两条成功续假，也不能仅依赖隐藏按钮限制。
- 续假批准前已产生的逾期申请标记、提醒和处理记录不删除；批准后新的未来检查按新截止执行，已发生事实与当前有效状态分别展示。
- 已确认人工销假待审核时不能新建或提交续假，入口提示先处理或结束现有人工销假申请；后端复核，不能仅禁用按钮。
- 人工销假被驳回或其他合法方式结束后，如请假链尚未完成销假且仍符合续假次数等条件，可再申请续假。人工审核通过或重打自动销假已结束整条请假时，不能再续假。
- 若续假先提交、随后出现人工销假待审，续假最终批准不得覆盖待审销假或绕过其核验；提示业务状态冲突，先处理销假。销假完成则关闭失效续假待办并保留历史，不能重新打开请假链。

### 8.5 已批准请假的取消申请

- 适用已批准但尚未出发、尚未完成销假的请假；学生从原单发起取消，填写取消原因，生成独立的取消申请。
- 已确认开始时间之后仍实际未出发也允许申请取消；表单要求学生明确声明尚未出发，说明情况，由中队长核实后审核，不能仅因已到开始时间拒绝。
- 不通过浏览器位置、是否超过开始时间自动推断学生已经或尚未出发；中队长保存核实意见，已实际出发的返校处理使用销假流程。
- 由所属中队长审核通过或驳回，保存申请人、原因、时间、审核人、意见和结果；驳回理由必填。
- 提交取消不立即使原批准失效。只有取消审核通过才将请假链标为已取消，关闭对应未处理事项和未来未归提醒。
- 审核通过不删除原申请、批准历史和已批准续假，保留取消结果；如果有关联待审续假等事项，以明确关联原因关闭其有效待办，防止取消后续假重新生效。
- 已取消请假不再进入销假或续假流程，不计入有效请假时长或人数，单独统计取消记录。
- 取消驳回不改变原有效批准区间；不把取消驳回改成原请假审批驳回。
- 已确认学生本人可在取消申请尚未审核时撤回，取消子申请变为“已撤回”，关闭该待办，保存撤回人、时间和关联记录；不删除原申请。
- 撤回取消不撤销原已批准请假，不改变已批准续假、有效截止、是否需要销假和未归检查，也不释放仍未结束请假的单条限制。
- 取消已经通过或驳回后不能再撤回；撤回与中队长审核并发时按当前状态原子处理，只允许一个结果成功。旧页面显示最新结果，不覆盖已完成取消。
- 已撤回后如仍符合未出发等条件，可重新提交新的取消申请，旧申请和撤回历史保留，不同时存在多条取消待办。
- 同一请假链最多一条待审取消申请，重复点击不重复建单；取消、销假、续假生效和负责人交接并发时，事务核验当前状态。
- 学生调班或负责人变化时，未处理取消待办同样按新关系自动交接并保留记录；已完成取消审核不改写原处理人。
- 未审批申请的本人撤销、已批准未出发的审核取消、返校后的销假是三个不同操作，界面、状态和审计分别记录。

## 9. 流程配置与审批

### 9.1 一期流程能力

- 采用表单式规则配置，支持顺序多级审批，不要求拖拽流程设计器。
- 管理员自主设置请假折算天数区间及其对应流程，配置节点数量、顺序和处理角色或人员；具体天数阈值与审批层级不写死在代码中。
- 基础匹配条件为时长；请假类型、组织、离校、外宿可作为配置的附加条件，未配置差异时不默认生成不同流程。
- 时长阈值、上下界是否包含边界及优先级必须清楚，配置时提示重叠和空档。
- 每个节点可指定人员，或结合学生班级、中队长、所属大队长及系部领导的有效管理关系解析相应角色审批人。
- 若同一节点解析出多人，须明确“指定一人”或“任一合格人员处理即可”的策略；一期不隐式启用多人会签。
- 展示流程名称、版本、状态、适用条件、节点顺序和审批对象。
- 提交时保存流程版本、节点及解析结果；流程修改不改写已提交申请历史。调班及各级管理关系变化触发的未处理节点自动交接按已确认规则执行，并保留交接前后记录。
- 不匹配流程、无审批人、审批人停用或权限失效时给出明确提示或异常待办，不自动通过或默认越级。
- 管理员转交异常在途节点时记录原因和历史，不能伪造原审批人的操作。

### 9.2 审批操作

- 审批待办展示学生、组织、类型、事由、时长、离校外宿、附件及前序结果。
- 支持通过、驳回和意见；驳回意见必填。
- 当前节点通过后进入下一节点；最后节点通过后标记已批准；任一节点驳回则结束审批。续假使用同一审批机制，最终通过时还须原子更新请假链的有效批准截止。
- 每次处理核验用户、账号、节点、权限、申请状态及数据范围。
- 状态变化、审批记录及下一节点创建保持事务一致，通知失败不反向撤销成功审批。
- 同时处理、重复提交只能形成一次有效节点结果。
- 申请详情完整展示审批时间线和节点状态。

### 9.3 批量审批

- 仅能选择本人有权处理的当前待办。
- 执行前展示选中数量和关键申请信息，支持共同意见。
- 每条独立校验及处理，返回成功、失败或已被处理的结果，失败不掩盖已成功记录。
- 每条保留审批人、意见、时间和批量操作关联，不能只保存一个批量结果。

## 10. 手机定位与销假

### 10.1 校区电子围栏

- 支持维护圆形及多边形范围、所属校区、启用状态、定位精度要求及边界容差。
- 已确认支持多个校区，回到任一允许销假的有效校区即可核验；学生所属校区用于资料及统计，不作为排他的返校范围。
- 后端从有效配置读取全部允许范围，只要命中其中一个即通过范围检查；记录实际命中的校区、围栏及版本，不相信客户端自行声明的校区。
- 圆形使用中心点和半径，多边形使用有效顶点集合，参数必须校验。
- 后端判断是否在允许校区内，不信任前端直接提交的核验结论。
- 明确浏览器坐标与围栏坐标所用坐标系；引入地图服务时进行必要转换，不能混用。
- 一期围栏可通过录入坐标及范围完成，不把外部地图平台账号作为启动依赖。
- 保存打卡使用的围栏版本或参数快照，后续调整围栏不改写历史核验结果。

### 10.2 正常销假流程

1. 学生打开已批准、未取消、已到开始时间且尚未完成销假的离校申请；非离校或尚未开始的申请不提供定位销假入口。
   - 若有已批准续假，显示同一请假链的最新有效截止；原单和续假不能分别重复销假。
2. 主动授权并获取当前位置，显示定位状态、精度和校区核验信息。
3. 后端检查是否离校、是否已开始、申请状态、坐标、精度、采集时间、任一有效校区围栏，以及是否超过有效批准返校截止。
4. 学生确认提交打卡，未逾期且定位核验通过时，在同一业务事务中记录打卡并自动完成销假，直接变为“已销假”。
5. 保存完成方式为“定位自动”、系统处理时间和规则结果，更新业务状态及相关提醒；不生成正常销假人工待办，也不伪造中队长确认记录。
6. 定位异常或逾期时不自动销假；学生补充相应说明，提交人工销假申请进入所属中队长审核。定位通过但逾期仍须人工审核。

### 10.3 打卡与审核记录

- 保存经纬度、精度、客户端采集时间、服务器接收时间、学生所属校区、实际命中校区、围栏、核验方式及结果。
- 服务端时间为提交和业务处理的依据；客户端时间用于辅助检查，不能独自决定是否逾期。
- 是否逾期以服务端接收有效提交的时间与批准结束时间比较，晚于批准结束时间即逾期；恰好等于结束时间不算逾期。预警宽限期只影响提醒，不延长自动销假的时限。
- 允许已开始请假在批准结束前提前返校销假；尚未到开始时间不能打卡，仅可申请取消。分别保存批准区间、打卡及完成时间，人工处理另存审核人和时间。
- 正常打卡仅在未逾期、后端核验和业务写入成功后显示已销假；网络失败不能仅凭浏览器定位成功提前展示完成。
- 待审核状态用于定位异常或逾期返校。中队长查看原因、位置及精度（可获取时）、批准截止、提交时间、逾期时长、说明、证明和历史后通过或驳回，驳回需填意见。
- 异常待审核期间防止重复生成申请；驳回后可重新打卡或补充异常申请，保留各次提交和处理记录。
- 已确认因定位失败进入人工待审后，允许重新定位打卡；重打时满足已开始、任一有效校区核验通过及未逾期条件，可直接自动销假。
- 自动完成时原人工申请标记为“已关闭：重新定位自动销假”，关闭其待办并保留提交内容和关闭原因，不伪造人工审核通过记录。
- 重打仍失败可保留原人工申请并追加必要定位尝试，不能生成重复人工待办；重打已逾期时仍需人工审核，不能使用旧定位或客户端时间绕过。
- 系统关闭人工待办与中队长审核并发时只产生一个有效销假结果；旧页面再次操作返回已处理状态。
- 支持批量处理异常销假，每条独立核验并保存记录。
- 自动销假、人工审核和重复请求并发时，只允许一次有效完成，原子地检查当前状态，不能重复销假。

### 10.4 定位异常

- 区分拒绝授权、设备不支持、获取失败、超时、精度不足、不在范围内、围栏未配置等原因。
- 未逾期且正常定位核验通过才自动销假；定位异常及逾期返校走人工入口，提交后状态为“异常待审核”，记录原因类别，不伪造正常打卡或系统自动完成结果。
- 逾期但定位通过的申请保留“定位通过”证据及逾期标记；中队长审核通过后保留逾期事实，不通过修改批准结束时间消除逾期。
- 人工核验需要学生说明或必要证明，由有权限中队长审核并填写核验原因。
- 已确认跨校区销假允许；不在任何有效校区范围内才判断为校区范围异常，停用校区不得继续作为有效返校范围。
- 不持续采集位置；定位记录只向相关学生及授权管理人员展示。
- 浏览器位置可能被伪造，系统不承诺仅凭坐标杜绝作弊；围栏、精度等后端核验仍必须执行，异常人工审核保留。未来如需门禁等额外证据，应另定对接范围。
- 开发模拟定位单独标记，仅开发环境可用，正式运行关闭。

### 10.5 不离校请假的结束

- 已确认不离校请假无需定位及人工销假，销假状态为“不需要销假”，界面展示已批准、未开始、进行中或到期已结束等实际阶段。
- 按当前有效批准结束时间推算到期结束；有最终批准续假则使用新截止，待审续假不提前延长。
- 不离校请假不进入返校打卡、未销假名单、逾期未归预警及中队长销假待办；普通审批及取消待办不受影响。
- 是否需要销假由已批准原单的是否离校字段确定，后端校验；不能通过打卡请求参数或续假擅自改为非离校以免除销假。
- 到期结束不是伪造自动打卡，也不产生人工审核人；原申请和统计保留，已取消则按取消规则排除有效统计。

## 11. 超时预警与站内消息

### 11.1 超时检查

- 仅对需销假的离校请假，按当前有效批准结束时间、宽限期和层级检查未归；续假批准后更新未来依据，历史提醒保留，非离校不生成返校逾期预警。
- 续假待审不暂停到期检查；超过旧截止仍显示未归或已有人工销假待审的实际状态，并标注“续假审批中”。续假批准后停止按旧截止新增提醒，不删除既有预警记录。
- 配置提醒对象、首次阈值和升级间隔；中队长、大队长等对应真实有效的负责人员。
- 明确区分“到期仍未完成销假”“到期前已提交异常申请、仍待审核”和“正常定位已自动销假”，异常待审不能直接视为未返校。
- 异常或逾期返校待审核过久可形成审核待办提醒，使用不同提示和规则；按时正常定位完成后无需等待中队长处理。
- 异常销假申请被驳回后，重新检查是否满足未销假预警条件。
- 撤销、驳回、取消审核通过、已完成销假或不需要销假的记录不生成未销假提醒；离校取消申请仅待审时仍按原有效业务检查。
- 相同申请、规则、层级的提醒去重；下一层升级、重试策略有明确状态记录。
- 服务启动后补查停机期间已到期记录，多实例或重复任务不生成重复有效提醒。
- 一期周期扫描间隔作为运行参数，不硬编码为学校规定。
- 界面展示任务最近成功检查时间及失败状态，避免任务停止但用户无法知晓。

### 11.2 通知和待办

- 事件包含普通请假及续假的新审批、流转、批准、驳回、撤销，定位自动销假结果、异常销假待审及结果、超时和异常事项。
- 包含已批准请假取消申请、取消待办、通过或驳回及本人撤回结果，通知状态与业务有效性分别记录，撤回后原取消待办不再可操作。
- 提供消息中心、未读数量、已读标记、待办列表和详情跳转。
- 待办依据实际业务状态关闭；“消息已读”不等于“业务已处理”。
- 跳转详情时重新校验权限，用户角色变化后不得凭旧消息访问越权数据。
- 已确认一期仅站内提醒和待办，不要求微信或短信主动通知，也不承诺关闭网页后收到系统级手机推送；浏览器或微信内打开网页后可查看未读及业务待办。
- 未来接入短信或企业微信时，外部通知失败独立重试，不能回滚已成功业务。

## 12. 查询、统计和导出

### 12.1 业务查询

- 学生查询本人请假、审批、销假和消息。
- 管理人员查询授权范围内申请、节点、打卡、销假及预警记录。
- 筛选项包含学号、姓名、组织、专业、年级、班级、校区、类型、时间范围、审批及销假状态、离校、外宿和超时情况。
- 支持组合筛选、排序、分页、筛选重置和详情查看；明确时间筛选是提交时间、请假重叠区间还是销假时间。
- 各页面常用条件保持一致，列表和导出使用相同权限及筛选口径。

### 12.2 报表维度

- 按班级或中队、大队、院系及全校汇总。
- 按学生个人、请假类型、校区、学年、学期或时间区间分析。
- 指标包含学生基数、请假人数、申请次数、批准时长、当前有效请假人数、未完成销假、异常待审核和逾期数量，并区分定位自动与人工审核完成的销假数量。
- 展示日、周、月趋势以及类型分布，支持查看指标对应明细。
- 配置频繁请假、累计时长等提示阈值，预警标记不能自动变成处分结论。

### 12.3 统一统计口径

- 请假人数按学生去重，次数按申请计数，二者不可混用。
- 有效请假统计基于已批准且未被审核取消的记录；驳回、撤销、取消和待审分别统计。原已批准后取消的历史不删除，但排除有效请假指标。
- 普通申请次数、续假次数分别展示，连续请假链合并统计有效期间；续假未批准不得计入有效延长天数。
- 请假天数主指标为“按实际时长折算的审批天数”（每 12 小时进位 0.5 天）。跨月或自定义统计区间先用精确时间交集计算各段实际分钟；分月展示以精确小时为主，折算天数应按所展示统计范围整体统一进位，并注明各月份分别进位的数值可能不等于整条请假链一次进位的结果，不得将二者混加。
- 实际经过时长须单独以小时或分钟展示，按精确时间区间交集计算；折算审批天数须另列，不能把未进位小时折算结果混同于审批天数。同一学生同一天多次不重叠请假的累计次数、申请天数总和与去重请假天数须明确区分。
- 批准时长、实际打卡时间推算的时长、销假完成时间分别命名和保存；人工审核时间单独记录，自动完成记录不虚构审核人。
- 当前有效请假人数包含已批准未取消且当前在有效区间内的非离校请假，以及同条件下尚未销假的离校请假；分别展示校内请假和离校请假，避免混为离校人数。
- 过期未销假、返校逾期及异常待审核仅统计需要销假的离校记录；非离校到期列为已结束，不进入未归名单。
- 正常定位自动销假、异常待审核、异常被驳回及未打卡分别显示；打卡或异常提交及时性与人工审核及时性分别判断。
- 历史组织统计默认按申请时组织快照；当前在读人数基数按当前有效学生资料，明确标注，避免误解比例。
- 展示统计截止时间、单位和过滤条件；未知实际离校时间时不能声称准确统计实际离校时长。

### 12.4 导出

- 支持查询结果、当月请假明细、组织统计和个人统计导出。
- 明细包含学号姓名、院系专业班级、类型事由、起止时间、时长、审批状态、审批人意见、打卡及销假状态等授权字段。
- 导出条件与页面一致，长结果不受当前页条数限制，但设置合理总量限制或分批处理。
- 导出学号保留前导零，中文及时间正确；对用户输入字段处理电子表格公式注入风险。
- 操作日志记录导出人、范围、条件、时间和结果。

## 13. 页面与交互要求

### 13.1 学生页面

- 登录、首次设置密码、修改密码及个人资料。
- 首页突出“申请请假”“审批进度”“返校销假”“消息”。
- 请假及续假表单、必传证明、个人申请列表、原单与续假的关联详情和审批时间线；已批准未出发请假的取消申请、待审撤回入口及结果；人工销假待审时明确禁止续假并提示处理入口。
- 销假打卡、自动完成结果、定位异常申请、人工审核结果和历史。
- 个人请假统计与站内消息。

### 13.2 管理人员页面

- 工作台显示本人待审批、异常销假待审核、未销假学生、超时及异常事项。
- 请假待办、申请详情、单条及批量审批。
- 已批准未出发请假的取消待办、原因和审核结果。
- 销假记录按定位自动和人工审核区分；异常销假待办支持查看详情、单条和批量审核，正常定位不产生确认待办。
- 权限范围内学生、请假记录、统计图表和导出。
- 手机端可完成核心审批；电脑端适合大表格、配置和批量处理。

### 13.3 管理员页面

- 学生及管理人员账号、角色和管理范围。
- 组织、专业、年级、班级、校区、负责人，以及大队长与中队长、院领导与系部的动态管理关系。
- 学生导入模板、预览、错误报告和批次记录。
- 请假类型、流程版本、节点及适用规则。
- 校区围栏、超时规则、基础参数、异常在途事项。
- 操作、导入及任务运行记录。
- 备份状态或操作说明入口；备份恢复可通过受控脚本完成，不强制开发浏览器数据库恢复界面。

### 13.4 通用交互

- 简体中文，桌面、平板、手机响应式适配。
- 普通手机浏览器与微信内置浏览器均支持核心业务；二者可分别登录，不要求跨浏览器自动共享登录状态。
- 手机列表优先展示关键字段和卡片详情，不能仅把电脑大表格缩小。
- 加载中、空数据、提交中、成功和失败均有清楚反馈。
- 禁止重复提交按钮只是体验措施，后端仍需保护。
- 表单校验就近展示，失败尽量保留填写内容；时间区间、审批结果及异常状态不只用颜色区分。
- 批量、重置密码、启停和其他影响较大操作提供操作对象和结果反馈。
- 手机附件支持拍照或从相册选择；上传失败允许重试。

## 14. 状态与一致性

### 14.1 状态分开保存

| 业务 | 状态 | 规则 |
| --- | --- | --- |
| 请假审批 | 待审批 | 已提交，尚无节点完成审批 |
| 请假审批 | 审批中 | 部分节点通过，后续未完成 |
| 请假审批 | 已批准 | 最后一个节点通过 |
| 请假审批 | 已驳回 | 任一有效节点驳回 |
| 请假审批 | 已撤销 | 本人按允许规则撤销 |
| 续假审批 | 待审批、审批中、已批准、已驳回、已撤销 | 与普通申请采用相同审批状态，但独立记录；仅最终批准产生有效延长 |
| 取消申请 | 待审核、已通过、已驳回、已撤回 | 所属中队长独立审核；仅待审核时本人可撤回，不改写原批准历史 |
| 请假链有效性 | 正常、已取消 | 取消申请通过才变为已取消；取消待审时仍保持原有效性 |
| 销假 | 不需要销假 | 非离校请假，按有效结束时间自然结束，不产生打卡或未归任务 |
| 销假 | 未申请 | 需销假的已批准离校申请尚未提交销假 |
| 销假 | 异常待审核 | 定位异常或逾期返校，学生提交人工申请，待所属中队长处理 |
| 销假 | 异常已驳回 | 中队长驳回异常申请，可按规则重新提交 |
| 销假 | 已销假 | 未逾期且定位通过自动完成，或定位异常、逾期返校经中队长审核通过；必须记录完成方式及原因 |
| 人工销假子申请 | 已关闭 | 因未逾期重新定位成功而由系统关闭，保留原因；不是人工审核通过或学生撤销 |

非离校、未批准、已取消或尚未开始的申请不进入正常销假流程。“未申请”可经开始后的按时正常打卡转为“已销假”，异常或逾期提交人工申请后转为“异常待审核”。定位异常待审可在未逾期重新定位通过后转为“已销假”，原人工子申请系统关闭。时间到期本身不能使离校申请自动销假。

### 14.2 必须一致的业务操作

- 请假创建与流程节点初始化。
- 审批结果、申请状态、下一节点与待办。
- 续假最终批准、原单及请假链有效截止更新、关联记录及后续任务依据。
- 取消审核通过、请假链失效、关联续假及人工销假等待办关闭、未来预警停止及历史保留。
- 本人撤回取消申请、取消子申请及待办关闭、撤回记录保存，原请假链和截止保持有效；与审核并发保护同样适用。
- 定位自动销假的打卡、系统完成记录、业务状态及预警关闭；异常销假的人工审核及上述关联状态同样保持一致。
- 学生导入时账号、资料和组织关联。
- 账号停用、密码重置及会话失效。

使用事务、约束和必要的并发控制保证一致性。数据库唯一约束保护学号、申请编号和提醒去重键等；前端判断不能替代后端校验。

| 逻辑对象 | 主要数据 |

| 人员管理关系 | 中队长与班级、大队长与中队长、院领导与系部、上下级、生效信息及变更历史 |
| 待办交接记录 | 关联节点或人工销假申请、原处理人、新处理人、交接操作者、时间、原因及结果 |
| 组织、专业、班级、校区 | 编码、名称、层级、负责人及状态 |
| 学生与组织变更 | 学号、基础资料、学籍、所属组织及历史 |
| 导入批次与结果 | 来源、操作者、结果数量、错误原因及时间 |
| 请假类型及规则 | 类型、附件要求、时间校验和启用状态 |
| 流程定义与版本 | 匹配条件、优先级、节点及发布状态 |
| 请假申请 | 学生、组织及规则快照、是否离校及销假要求、精确时间、实际分钟数、半天进位折算天数、补假标记及原因、参考经过时长、状态、版本 |
| 续假及请假链 | 原申请、续假编号、当前及目标截止、累计匹配天数、最多一次成功续假限制、重提关联、逾期提交原因及标记、有效批准版本、状态和生效历史 |
| 取消申请及审核 | 原申请或请假链、取消原因、未出发声明、提交时间、处理人、核实意见及结果、本人撤回状态和时间、请假链失效时间 |
| 申请流程节点及审批记录 | 实际处理对象、节点结果、意见及时间 |
| 附件 | 安全存储标识、原文件名、类型大小、所有者及业务关联 |
| 围栏及版本 | 校区、形状、坐标系、参数、容差、精度要求 |
| 销假申请、打卡及处理 | 位置精度、实际命中校区及围栏、核验结果、自动或人工完成方式、重打记录、人工子申请关闭原因、处理时间及必要审核人 |
| 预警规则与事件 | 阈值、对象、层级、状态及去重信息 |
| 通知及待办 | 收件人、事件、关联业务、已读及处理信息 |
| 任务运行记录 | 最近执行、成功失败、错误及处理摘要 |
| 操作日志 | 操作者、动作、对象、时间、结果及必要前后值 |

- 关系和外键或等价约束清楚，历史数据不因基础资料停用而断链。
- 时间采用统一存储约定，推荐 UTC 存储、北京时间显示；导入、查询、后台扫描和导出统一换算。
- 配置和数据迁移有版本记录；任何升级不默认清库或重新覆盖用户资料。
- 审批用折算天数保存为可表示 0.5 的精确数值（推荐以“半天数”整数或 DECIMAL 保存，禁止浮点误差），另存实际分钟数及计算规则版本；不能保存为整数天或混同实际时长。
- 常用列表、学生、状态、组织、时间、待办和到期扫描条件建立合适索引。

## 16. 附件、安全、性能和可靠性

### 16.1 附件

- 配置允许类型、单文件大小、数量及总量，不接收任意可执行文件。
- 所有普通请假及续假类型必须关联至少一份有效证明；缺失时前端提示、后端拒绝提交。取消申请和人工销假的材料要求单独规定，不将本条自动扩大到所有业务表单。
- 服务端检查扩展名、类型和必要文件特征，生成安全存储名，防止路径穿越和覆盖他人文件。
- 私有附件不放在无权限控制的 public 静态目录。
- 下载、预览均检查当前用户的业务访问权限。
- 上传与申请关联失败时有孤立文件回收机制，不能误删已被有效业务引用的文件。
- 文件删除及保留策略可配置；历史证明默认不因普通操作删除。

### 16.2 安全

- 服务端统一执行输入校验、认证、数据范围及状态校验。
- 不在浏览器、日志、错误页面或仓库暴露数据库密码、认证密钥和会话凭证。
- 数据库使用应用专用账号；迁移和日常运行所需权限明确，不长期以 root 执行普通业务。
- 限制登录尝试、异常上传和大批量请求；错误信息不泄露私有资料。
- 审批、销假、权限、密码、导出和配置变更可审计；日志脱敏且普通用户不能修改。
- 按用户隔离动态业务数据和缓存，不缓存出可能向其他用户泄露的个人页面结果。

### 16.3 性能与容量

- 以不到 8000 学生的资料规模作为本地模拟数据目标，另外准备管理人员及适量历史申请。
- 用户总数不作为同时在线或并发请求数；按日常分散访问及集中请假、销假场景压测。
- 列表分页、必要索引、有限批量及附件限制优先于引入复杂基础设施。
- 大导入、批量审批和导出避免长时间阻塞所有交互；需要时分批执行并展示进度。
- 具体并发目标、响应时间及服务器配置在测试前记录；未经实测不承诺全体学生同时操作的容量。

### 16.4 备份与恢复

- 提供数据库和附件备份脚本、配置说明及恢复手册，备份不包含可直接公开的凭证。
- 数据库备份与附件快照记录关联时间；恢复方案能维持业务与附件对应。
- 备份放在可配置目录，避免与源数据共用唯一副本；保留数量及周期可配置。
- 恢复前明确目标环境和影响，先在独立测试数据库及目录演练，不覆盖唯一现有数据。
- 交付前至少完成一次实际恢复验证，不能仅以成功生成备份文件作为验收。
